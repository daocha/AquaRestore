# Referral and unlock data disclosures

This is operator guidance for store declarations. The user-facing policy is [PRIVACY.md](../PRIVACY.md).

A configured backend collects data off the device. **Every install with a configured backend sends its device identity at first launch, whether or not the user ever uses referrals.** Server unlock redemption adds a redemption history. A persistent hash is a pseudonymous device identifier, not anonymous data.

The backend receives the package/bundle ID and app-scoped SHA-256 device identity. It stores a registration record for each device, referral ownership, immutable referrer attribution, credit totals, verified credential/key bindings, challenge/security records, and unlock redemptions (device hash, code ID, granted features and timestamp). Platform attestation proofs are processed for verification. Raw Android ID/vendor UUID is not sent. The hosting provider or reverse proxy may also retain IP/access logs; audit its actual configuration. Unlock codes are sent over HTTPS. Redemption matches an app-scoped digest, and the server also keeps the plain text of each code for the operator's list command. They are operator-issued secrets, not personal data, but the database and its backups must be protected accordingly.

For store declarations, review **Device ID / Device or other IDs** and applicable **Product Interaction / App interactions** for device registration, referral submissions and unlock redemption, used for app functionality and fraud/security prevention. Apple treats data tied to a persistent device identifier as linked to the user unless its unlinking criteria are met. Do not declare "no data collected" for an app using this service. Complete the forms against the actual production deployment and any other SDKs in the app. `ios/AquaRestore/Resources/PrivacyInfo.xcprivacy` currently declares no collected data, which is wrong for a build with a configured backend; update it before shipping one.

First-party access control alone does not constitute Apple's cross-company advertising/data-broker tracking, and does not by itself require an ATT prompt. Review this again if the data is later reused or shared for tracking. The short inline notice at redemption explains the device identifier record; it does not replace the published privacy policy or store declarations.

Before deployment, the operator must document the real retention period, deletion/request contact and process, hosting/processors, purposes and sharing practices in the privacy policy. The current backend retains attribution and redemption records indefinitely to preserve lifetime binding and quota enforcement; it does not provide a user-facing deletion endpoint. Deleting these records can remove recovered access, restore code capacity or allow repeat referral claims. Choose and implement a retention/deletion policy consistent with the applicable requirements instead of promising automatic deletion that the service does not perform. Keep the SQLite volume and backups protected.

When no backend URL is configured, this feature sends no referral/unlock requests and shows no referral controls; disclosures must still account for other app functionality.

Sources: [Apple app privacy details](https://developer.apple.com/app-store/app-privacy-details/), [Apple privacy and tracking](https://developer.apple.com/app-store/user-privacy-and-data-use/), [Google Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [Google Play user data policy](https://support.google.com/googleplay/android-developer/answer/10144311).
