# Referral API integration

## App configuration

Set the backend base URL in AquaRestore's repository-root, gitignored `.env`:

```dotenv
AQUARESTORE_REFERRAL_BACKEND_URL=https://referrals.example.com
```

Do not append `/v1` or `/health`. Android and iOS Debug/Release builds read this setting; exported variables override `.env`. Rebuild after changes. Release requires HTTPS. With no URL, both batch features are available and referral/Unlock Code controls are hidden. With a URL, features require a saved grant, referral progress or server-issued unlock code. Unlock codes are not stored in `.env`.

## Requests and responses

The full reference with sample payloads is `API.md` in the referral server's repository. All paths below are relative to the configured base URL. Requests and responses use JSON. `{app}` is the actual package/bundle ID (`com.aquarestore.app.debug` or `com.aquarestore.app`); `{deviceHash}` is the app-scoped, lowercase 64-character SHA-256 identity generated by the app. Debug and Release identities and grants are separate.

### Register the device

`POST /v1/apps/{app}/devices/{deviceHash}/register` with body `{}`. The app calls it once, on first launch, so friends can use this device's code. It sends no attestation proof and grants nothing. It returns HTTP 200 with the access state below plus `alreadyRegistered`:

```json
{
  "referralCode": "40094aXX1F",
  "referralCount": 5,
  "referredByCode": "0000000001",
  "unlocked": {"batchPhoto": true, "batchVideo": false},
  "alreadyRegistered": true
}
```

The app shows its referral code immediately, using the same formula as the server. On any 200 the app saves that it is registered, for this backend and device identity, and the returned `referralCode`, which it shows from then on because it wins if the two differ. It then never calls again, except that an install registered before codes were saved registers once more. It also saves the returned state, which restores the referrer and grants after app data is cleared, so `alreadyRegistered: true` is not an error. On any failure it saves nothing and retries silently on the next launch. Tapping **Invite** also retries, so a device that was offline at launch exists on the server before a friend tries its code.

### Read access state

`GET /v1/apps/{app}/devices/{deviceHash}` returns HTTP 200:

```json
{
  "referralCode": "40094aXX1F",
  "referralCount": 5,
  "referredByCode": null,
  "unlocked": {"batchPhoto": true, "batchVideo": false}
}
```

`referredByCode` is the permanent referrer code, or `null` before attribution. The app uses the returned feature booleans as grants. Tapping a locked batch action performs this single read; Settings and already-unlocked batch actions make no request. Positive grants persist locally across updates and are never revoked by a negative response or API error.

### Submit a referral or unlock code

First obtain a challenge with `POST /v1/apps/{app}/devices/{deviceHash}/challenge`:

```json
{"action":"referral","referralCode":"40094aXX1F","platform":"android","keyId":"<credential-id>"}
```

For an unlock code, replace `action` and the code field:

```json
{"action":"unlock","unlockCode":"<server-issued-code>","platform":"android","keyId":"<credential-id>"}
```

Expected HTTP 200 response:

```json
{"challengeId":"<id>","clientData":"<base64url-bytes>","expiresAt":1900000000,"attestationRequired":false}
```

Challenges expire after 120 seconds. Decode `clientData` and generate proof using those exact bytes:

| Platform | `keyId` | `proof` fields |
| --- | --- | --- |
| `android` | Fresh random UUID per submission | `certificateChain` (leaf-first base64url DER certificates), `signature` (base64url DER ECDSA) |
| `ios` | App Attest key ID | `assertion` (base64 CBOR), plus `attestation` (base64 CBOR) when `attestationRequired` is true |
| `debug` | Full device hash | `token` (debug authentication credential) |

Android generates a fresh P-256 Keystore key with SHA-256 of the decoded bytes as its attestation challenge, signs the original bytes with SHA256withECDSA, and deletes the temporary key after constructing the proof. iOS uses SHA-256 of the decoded bytes as App Attest's client data hash. The existing `ReferralProof` implementations handle these operations. The same Android proof works for GitHub and Play APKs when their signing certificates are allowlisted; no Google Cloud configuration is needed.

Then POST to `/v1/apps/{app}/devices/{deviceHash}/referral` or `/unlock`, matching the challenge action:

```json
{"challengeId":"<id>","proof":{"<platform-specific-field>":"<value>"}}
```

The challenge rejects a referral code with HTTP 400 `invalid_referral_code` if it is malformed, is the device's own code, or has no registered owner in this app. The app tells the user the code is invalid, and checks format and self-referral itself first. A device that already has a referrer skips the owner check, so it reaches the 409 below.

Success returns HTTP 200 with the same access-state shape as GET. A same-referral retry adds no duplicate credit; a same-device/code unlock retry consumes no additional use. Attempting to change an existing referrer returns HTTP 409 **with access state**, including the original `referredByCode`; the app restores that value and shows it as a label instead of the input. Used proofs cannot be replayed; an explicit retry needs a new challenge. iOS may obtain a replacement challenge/key after interrupted enrollment.

### Errors

Errors return `{"error":"<code>"}`, with an optional `message`. In particular:

| HTTP status | Error | App behavior |
| --- | --- | --- |
| 400 | `invalid_referral_code` | Say in a popup that the referral code is invalid and keep the input editable |
| 400 | `invalid_unlock_code` | Show incorrect unlock code inline |
| 409 | `unlock_code_exhausted` | Show maximum-use error inline |
| 401 | Verification failure or replay | Show submission failure inline |
| 429 / 503 | Rate limit / service unavailable | Show failure inline; preserve existing access |

The exhausted response is `{"error":"unlock_code_exhausted","message":"Unlock code exceeding max consumption."}`. Distinguish an error body from the referral-conflict state body even though both can use HTTP 409. Other malformed responses and network failures also remain inline and must not block unlocked features or ordinary editing/export.

## Debug verification bypass

To test the actual API from a simulator or directly installed debug APK, configure:

```dotenv
AQUARESTORE_REFERRAL_BACKEND_URL=https://your-test-backend.example.com
AQUARESTORE_REFERRAL_DEBUG_VERIFICATION=token
AQUARESTORE_REFERRAL_DEBUG_TOKEN=<credential-provided-by-the-server-operator>
```

The credential must match the server's configured debug credential (at least 32 base64url characters), and the server must allow `com.aquarestore.app.debug`. Rebuild both apps. They submit `platform: "debug"`, the device hash as `keyId`, and `proof: {"token":"..."}`. This bypasses only device attestation; a valid server unlock code or earned referral grant is still required, with the normal usage limits. Enter the operator-issued unlock code in Settings → Developer tools → Unlock Code (tap the version ten times to reveal Developer tools).

For a backend on your Mac, use `http://127.0.0.1:8080` from the iOS simulator, `http://10.0.2.2:8080` from the standard Android emulator, or `http://<Mac-LAN-IP>:8080` from physical devices. The server must be reachable at that address. Debug permits HTTP; production requires HTTPS.

Set `AQUARESTORE_REFERRAL_DEBUG_VERIFICATION=platform` to exercise real Apple/Google proofs instead; it never falls back to the token. Simulators and devices without supported hardware attestation may not satisfy real verification. Release builds never include the debug credential or use the bypass. Production Android requires a supported valid hardware-attestation chain and locked Verified Boot. GitHub and Play distributions use the same policy.

Server deployment, credential provisioning, code creation and administration belong in the referral server's README. Privacy declarations are covered separately in [Referral privacy](REFERRAL_PRIVACY.md).
